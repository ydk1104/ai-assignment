1. 이제 워커에 옮겨줘. 워커에 옮기면서 추가로 다음을 구현해줘.

토큰을 생성하는 동안, 20~80ms 사이의 무작위 지연이 필요해. 단, 테스트를 할 경우에는 10ms의 지연만으로 될 수 있도록, env가 production인지 dev인지에 따라 다르게 빌드하도록 해줘  
10% 확률로 생성 중간에 에러를 내도록 해줘. pickTokenCount 실행 후, 에러 여부를 정하고, 에러가 발생한다면 0~pickTokenCount()중 어디서 에러가 발생할 지 정한 다음, 실제로 토큰을 생성하면서 지연을 계속하다가 해당 시점에 token_create_fail 에러를 발생시켜줘.  
토큰 생성 도중에는 redis에 메모해줘. 토큰 생성에 지연이 존재하는만큼 같은Idempotency-Key로 두 번의 요청이 서로 다른 API서버에 들어갈 수 있으므로, 이미 생성중이라면 처리중입니다. 로 회신할 수 있어야 하기 때문이야

요청이 오면 먼저 원장에서 완료 여부를 보고, 없으면 Redis에 SET NX로 "생성 중" 메모를 남겨요.  
이미 메모가 있으면 409와 처리중입니다.를 돌려줘요. 같은 키에 다른 body가 오면 422예요.  
메모에는 TTL 30초를 걸고 워커가 생성 중에 계속 연장해요. 워커가 죽어도 영원히 "처리중"으로 남지 않아요.  
메모를 잡고 나서 원장을 한 번 더 확인해요. 다른 서버가 방금 끝낸 경우에 중복 생성되는 것을 막기 위해서예요.

제가 정한 부분 (바꾸고 싶으면 말씀해 주세요)

실패한 생성은 원장과 합계에 기록하지 않아요. 메모도 지워서 같은 키로 재시도할 수 있어요. 실패 시점까지의 토큰을 과금하려면 구조를 바꿔야 해요.  
이어받기(Last-Event-ID)는 생성이 끝난 뒤에만 돼요. 생성 중에 같은 키로 다시 오면 3번 요구대로 409예요.  
클라이언트 연결이 끊겨도 워커는 끝까지 생성하고 원장에 기록해요.  
소요 시간이 길어졌어요. maxTokens 1000이면 토큰이 300~1000개라서, 개발 모드는 약 3~10초, production은 약 15~50초가 걸려요. 상한(1,000,000)에 가까운 값을 보내면 몇 시간이 걸리니, 상한을 낮출지 정해 주세요.
