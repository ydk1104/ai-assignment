## 실행 방법

```
docker compose up -d --build # 실행
npm run test:docker # 테스트
```

## 명세와 다른 설계

"생성 중인 토큰은 서버 사이에서 공유되어야 합니다"가 의도한 부분이라 하셨으나, 현재는 워커에서 생성 완료 후에 DB에 저장하므로, 생성 중인 토큰이 공유되고 있지 않습니다.  
이는 시나리오 5. LLM 실패를 고민하면서, LLM의 문제로 인한 실패는 과금되지 않고, 실패 시점까지 처리된 토큰을 유저에게 내보내지 않는게 옳다고 판단하였기 때문입니다.  
그러나 메일 질답 이후, 유저에게 보내지 않더라도 서버간에서는 redis에 정보를 올려서 참조하도록 하거나, onToken 이벤트를 구독시키는 등의 방안으로, 생성중인 토큰 또한 읽을 수 있게 해놓는게 올바른 동작이겠다는 생각을 하였습니다.  
이는 1. DB에서 읽어오는건 공유 방안중에 제일 느린 방안이고 2. 생성 완료 후에 토큰을 읽어온다면 유저 입장에서 토큰을 실제로 받아지는게 늦어지기 때문입니다.  
사실 지금도 documents.controller의 attach나, document-queue.service의 JobListener를 참고해보면 이벤트를 구독하는 로직은 있는데요.  
api서버 자기자신의 job만 구독하는 방식이라, 시나리오 3. 재시도 항목에서 다른 api서버로 붙었을 때는 무조건 디비에서 읽을 것이기에, 해당 설계는 먼저 설명을 남기며 시작해보도록 하겠습니다.

## 시나리오 처리

1. 동시 요청  
   동작: 잔액이 100인 상태로 maxToken=60의 요청이 5번 올 경우, 두번째 요청부터는 거절합니다.  
   앞선 요청에서 token을 덜 소모해서 두 요청이 성공할 수도 있지만, 서비스 특성상 해당 경우에서 사용자의 올바른 동작은 잔액을 충전하기, 혹은 maxTokens을 낮춰서 다시 요청하기일거라 생각하였습니다.  
   UX를 보다 고려한다면, 다른 방안으로는 바로 거절하는 대신 대기큐에만 넣어둔다거나, 큐까지 쓰진 않더라도 하나의 요청정도는 예비로 킵해놓는 등의 방안도 괜찮으리라 생각하지만, 구현 난이도에 비해서는 UX 개선이 크지 않으리라 생각했습니다.  
   테스트: e2e-basic.js 423 line, 같은 유저가 동시에 여러 번 요청해도 크레딧이 음수가 되지 않는다 (예약) 항목으로 보장합니다.  
   현재 잔액의 40%만큼의 요청을 3번 보내고, 2번만 성공함을 확인합니다.

2. 재시도  
   동작: AI의 제안을 받아들였습니다. 기본적으로 409 Conflict로 처리합니다.  
   현실적으로 구분할 필요가 있는진 고민되지만, Idempotency-Key가 같지만 prompt가 다른 경우, 422로 별도 처리하고 있습니다.  
   테스트: e2e-basic.js 227 line, '생성 중에 같은 키로 다시 요청하면 409 "처리중입니다.", 다른 본문이면 422, 취소하면 확정된다' 항목으로 보장합니다.  
   작업중에는 scripts/resume-test.js를 사용해 확인했습니다.

3. 재접속  
   동작: 기본적으로, API 명세에 따라, SSE Last-Event-ID를 참고하여 처리합니다.  
   테스트: e2e-basic.js 175 line, "같은 키로 다시 요청하면 DB에 저장된 같은 내용이 재생되고, Last-Event-ID 다음부터 이어받는다"와 2. 재시도의 테스트 결과로 보장합니다.  
   nginx가 RR 로드밸런싱으로 해두었으므로 연달아 보내면 무조건 다른 서버로 들어간다고 가정했다는 점, 명세와 다르게 3초 대기가 없다는 점 등의 차이가 있지만,  
   DB를 참고하는 현재 설계에서 동작을 보증하는데에는 Last-Event-ID부터 받아오는지, 여러번 받아도 제대로 받아오는지만 검증한다면 재접속 항목을 확인하기 충분한 테스트라 판단하여 추가 작업은 하지 않았습니다.  
   작업중에는 scripts/disconnect.js를 사용해 확인했습니다.

4. 취소  
   동작: 명세대로, 1초안에 중단하고, 생성된만큼만 과금됩니다. 이 경우 해당 부분까지의 작업은 완료된거라 생각하여, (userId, prompt, maxTokens=취소 시점)요청을 완료한 것과 동일하게 취급합니다.  
   테스트: cancel-test.js로 확인합니다.  
   자동화된 테스트에도 있지만, 로직이 흩어져있어서 수동 테스트로 확인하는게 보다 보기 편하시리라 생각합니다.  
   `# docker compose up -d` 이후 `# node cancel-test.js`를 통해 확인할 수 있습니다.

5. LLM 실패
   동작: 취소와 달리 에러로 인한 문제는 과금되지 않는게 맞다고 생각하여, 나간 토큰에 대해서 크레딧을 부과하지 않고자, 생성 완료 후부터 스트림을 흘러보냅니다.  
   클라이언트는 token_create_fail 메세지를 받게 됩니다.  
   테스트: e2e-failure.js로 확인합니다.  
   seeds.json에 있는 failure:120 시드를 사용하여, 정해진 위치에서 에러가 발생하는지 확인하는데, 크레딧 관련 확인 작업은 빠져있어 이를 보증하지 못하고 있습니다. (2320 토큰으로 수정예정)

6. 워커 중단
   동작: 다른 워커에서 처음부터 재생성합니다.  
   앞서 설계에서 문제되었던 점대로, 생성 도중에 스트림을 흘려보내지 않아서 처음부터 재생성하도록 구현되었습니다.  
   테스트: e2e-failover.js로 확인합니다. `/containers/${id}/kill` Docker Engine API를 사용합니다.  
   현재 워커 서비스가 죽는거랑 kill -9로 죽이는게 동치인거로 알고있긴한데, kill -9로 죽여서 확인할때는 scripts/failover-test.js를 통해 재현할 수 있습니다.

## 추가 질문

1. 워커가 30초쯤 멈췄다 깨어나면 어떤 문제가 생기는가?  
   해당 시나리오에서 문제되는건 보통 이중과금이라고 생각합니다.  
   워커가 죽으면서 TTL을 연장하지 못함 => redis에 TTL 삭제 => 다른 워커가 job 챙겨감 => 원래 워커가 깨어나면서 두 워커에서 동시에 진행과 같은 사례가 가능하기 때문인데,  
   현재도 클로드가 "메모를 잡고 나서 원장을 한 번 더 확인해요. 다른 서버가 방금 끝낸 경우에 중복 생성되는 것을 막기 위해서예요."로 처리해서 이부분은 괜찮을 것 같다고 생각합니다.
2. 이 설계가 깨지는 조건, 그리고 실제 서비스라면 더 해야 할 일
   LLM Token을 짧은 길이의 string으로 가정했는데, 응답이 코드를 생성하기도 하므로, 면접에서 말씀드렸던것과 같이 s3등의 외부저장소를 고려해야할 것 같습니다.  
   또, 실제로는 응답 하나도 여러 Token으로 구성되어 있는 것으로 알고있는데요. 제가 생각하는 일반적인 의미의 Token이 맞다면, 어느정도 단위로 묶는 작업이 별도로 필요할 것 같습니다. (DB에 저장하거나, 유저에게 보내거나 모두, 일반적인 Token은 하나씩 흘려보내기에는 너무 작은 단위라고 생각합니다)  
   메일에도 적었지만, DB에 관해서가 좀 아쉬워서 해당 부분을 많이 신경쓸 것 같습니다. lock도 과하게 걸고 있다고 느꼈고, 이게 스키마 설계부터 엮인 이슈라 생각되네요.  
   기존 LLM의 응답을 보여주는것도 과제에서 작업한 API server의 롤이라면, (아무래도 turbo repo 사용하시는것도 그렇고 마이크로서비스 설계 지향하시는것같아서요)  
   DB 성능이나 요금을 보다 고려해보면 좋을 것 같은데 하지 못했기에 아쉬움이 남네요.
3. 시간 안에 못 한 것과, 했다면 어떻게 했을지
   테스트를 좀 더 유의미하게 정리하고 다듬었을 것 같습니다. 현재 unit test같은건 1+1=2를 검증하는 수준의 테스트도 있어서요.  
   failover 테스트가 오래 걸려서 테스트가 분단위로 걸리고 있고, scripts/*.js를 실행하는 자동테스트는 단계로 카운트가 안되고 있기도 하고 아쉬운 점이 좀 있는 상태입니다.
